# Learnings — Active Guidelines

Distilled from 40 past learnings (archived in `past_learnings.md`). These are principles to apply going forward.

---

## Current Critical Guardrails

- **AQL/Zopedia has one orchestration spine.** Chat, live research, homepage summary, page summary, evidence-pack generation, critique, and maintenance are modes of one engine contract. Do not add or extend feature-specific LLM/research endpoints when the work belongs in the shared AQL/Zopedia engine.
- **Memory/wiki/tool access is a product contract, not an optional helper.** Any research-grade AQL, Attention, Summary, SAA, or Zopedia surface should enter through the shared engine so it gets the same planning, tools, evidence pack, memory reads, critique, and write policy.
- **Before touching Zopedia/AQL/Attention/SAA LLM paths, read `documents/reference/AQL_ZOPEDIA_ENGINE_GUARDRAILS.md`.** The long numbered list is history; the reference file is the active operating rule for this failure zone.
- **Tool boundaries repair tool-contract failures before product answers.** If an LLM emits malformed but recoverable tool arguments, such as flattened Python or stringified dataset refs, normalize and run one bounded repair at the shared tool boundary. Do not let a code-generation error become a false "data unavailable" answer.
- **Analysis repair must be execution-proven, not just attempted.** A repaired Python string can still fail on indentation, missing columns, timezone joins, or hidden stdout. Give the repair pass actual input schemas/samples, allow safe pandas methods, normalize narrow generated-code formatting defects in the sandbox, and expose stdout/tables back to synthesis before calling the tool path fixed.

## Architecture

1. **One source of truth, one shared contract.** Shared behavior lives behind one execution core. Streamlit, REST, and MCP are thin facades. Datasets, charts, artifacts, and auth scopes are first-class objects — not UI text other clients parse.
2. **Fix at the source, not in the UI.** If a summary or dashboard is wrong, fix the upstream data or service path. Build rollups from the same payloads used by detail views so they cannot drift.
3. **Persist important product state as first-class data.** If something must appear in the product, it needs a dataset or event — not a narrative side effect. Usage telemetry comes from durable DB events, not container logs.
4. **Config-driven over hardcoded.** Mappings, thresholds, and graph definitions go in versioned config or data files. When deterministic and retrieval-backed logic both contribute, update one shared status contract.

## Operations

5. **Azure runtime is the source of truth.** Local generated files are fallback only. Normalize equivalent env vars to one setting. Standardize on one Key Vault.
6. **Image promotion and env promotion are separate.** A promoted image digest does not carry new env keys. Deploy scripts must manage both.
7. **Identity-driven jobs need deploy-time sync and runtime fallback.** Attach the managed identity on every update. Fall back to the default attached identity when the configured client id is stale.
8. **Scheduled jobs fail on missing mandatory inputs.** A green skip for a required dataset hides stale data and delays incident detection.

## Security

9. **Source-control discipline and fail-closed defaults.** Any secret in a tracked file is compromised. Notebooks and legacy folders are full scan scope. Auth paths fail closed when dependencies are unavailable.
10. **Token-signing keys have their own lifecycle.** Do not borrow user passwords for signing. Browser-readable cookies are a workaround, not a design.
11. **Telemetry before credentials.** Enable auditing and diagnostics before or alongside any rollout that introduces real credentials. Missing audit trails are security defects.

## Testing & Validation

12. **Smallest callable unit first, then the full user path.** Reproduce issues at the store/service level, then verify the exact runtime path the user hits — including materialized and cached paths.
13. **Raw SQL gets a direct store test.** Service tests are not enough when the bug is in a SQL string.
14. **Streamlit changes need render checks.** `AppTest` verifies block order and visible text. Seed `_ui_user_context` for admin pages. Check presence and absence.
15. **Azure CLI success does not prove app-runtime RBAC.** Verify at least once from inside the live container with the app's actual managed identity.

## Evidence & Retrieval (AQL / SAA)

16. **One shared evidence trace.** All research paths route into `search_results -> source_documents -> evidence_chunks -> claims`. No parallel corpora.
17. **Retain the richest text available.** Prefer page text > provider text > snippet. When a source is worth opening, its text budget must be large enough to matter.
18. **Storage, then access, then retrieval.** First: stable document ids and durable blobs. Second: a shared search and document-open contract. Third: chunk history. Fourth: hybrid retrieval. Do not skip steps.
19. **Chunks are the reasoning unit.** Persist chunk history at write time. Keep the searchable unit aligned with what the pipeline actually reasons over.
20. **Match signals separate from rerank signals.** Lexical and semantic overlap determine match. Authority and freshness determine rank order.
21. **Vendor bulk endpoints are optional.** Keep the stable per-series path available. One shared payload shape behind both strategies.

## Agent Quality

22. **Retrieval before choreography.** Fix retention and retrieval before adding multi-agent orchestration. Advanced patterns do not rescue weak evidence.
23. **Agent tools must match the product promise.** If the feature promises search-backed analysis, the tools must include the actual research sources. The model cannot use tools it cannot see.
24. **Internal evidence first, external search second.** The SAA retained evidence store is a high-value, low-latency source. Agent prompts should direct the planner to search retained evidence before calling live web search APIs. This avoids missing evidence the system already has and reduces latency.
25. **Preserve the user's query phrasing through the search pipeline.** Intent classification is useful for routing but strips domain-specific terms. The original query text must reach the search API to avoid losing key phrases like "short squeeze" that the classifier maps to generic categories.
24. **Gap detection over source count.** A system can browse and search broadly but still sound flat if it compresses evidence too early and never asks what is still missing.
25. **Different surfaces need different writers.** Homepage summaries, narrative cards, and audio need different density and evidence presentation. Do not reuse one compact format for all.
26. **Generic phrasing triggers another research pass**, or at minimum a clearer "unresolved" explanation. Accept `"no clear catalyst"` only when the system has actually searched and found nothing.
27. **Consolidation should preserve shims while moving ownership.** When retiring legacy Attention reasoning paths, first move the source function into AQL/compute/Attention-owned signal modules, then keep thin compatibility imports until pipeline jobs, presentation loaders, and tests are retargeted.
28. **Single-shot LLM summaries hallucinate specifics; ground them with a critique+judge layer.** When the synthesizer LLM only sees text beats (no numerics, no source claims), it will invent percent moves and contradict its own catalyst names. The fix is two extra personas after synthesis: a critique agent with a focused tool subset (price lookup, evidence search, recent news) that flags numeric/contradiction/unsupported issues, and a judge LLM that rewrites only the flagged passages. Both must be best-effort with fall-through to the original summary so the pipeline stays robust. Pattern lives in `services/aql/critique.py`, wired into `build_attention_agentic_summary_with_trace`.

## LLM Integration

27. **All user-facing narrative is LLM-generated.** No `f"Oil is {direction}"`. No if/elif dispatch for narrative variation. Structured data goes into the LLM prompt; natural language comes out.
28. **LLM readiness is verified at startup.** `check_llm_readiness()` logs provider, model, deployment, and embedding status. "Embedding client exists" does not mean "embedding deployment is provisioned."
29. **Research browsing degrades cleanly.** Use Playwright when available, fall back to HTTP extraction. Keep planner bias soft — encourage tools, do not force fake research loops.
30. **Gated-source auth fails fast.** Fetch the target page first, authenticate only when gated. A slow fallback is still a broken product path.

## UI & Product

31. **Actions before containers.** Start with what the user needs to do per row, then pick the UI component. Backend mutations before UI polish.
32. **No implementation details on user screens.** Architecture explanations go in docs. If the text does not change the next click, remove it.
33. **Every word the user reads must add information.** The token-to-information ratio is the most important UX metric for LLM-generated content. Internal quality signals (critique summaries, review assessments), raw tool/source names (Investigator.Company Context, Dataset.Recent News), and verbose "we found nothing" paragraphs are waste. If there's no catalyst, say "No catalyst identified" — not a 40-word paragraph explaining that the absence of evidence is accurately reflected. Confidence labels only appear when high. See `documents/architecture/UI/ENRICHMENT_PHILOSOPHY.md`.
33. **Loading states reuse real backend stages.** Surface the agent's actual reasoning and tool calls — do not invent a generic progress bar. Keep the trace visible after completion.
34. **Precompute expensive media in the job.** TTS and heavy enrichment run in the scheduled job and persist with the snapshot. On-demand fallback is recovery, not the primary path.
35. **Tabs evaluate all bodies.** For heavyweight admin screens, use `st.segmented_control` with conditional rendering instead of `st.tabs`.

## Caching

36. **Local cache is disposable.** Blob storage + manifests are the durable layer. Cache caps and pruning live in the shared cache helper.
37. **Derived summaries rebuild from raw data on read.** Treat stored summary tables as performance convenience, not independent authority. Check whether a broken derived field can be recomputed before debugging the UI.

## Macro Dashboards

38. **Three lenses: hard data, market pricing, transmission.** Inflation, labor, and housing activity alone are not enough. Add curve shape, real yields, breakevens, dollar, and bank-credit flow early.

## Documentation

39. **Move stable architecture out of task plans.** Durable design docs belong under `documents/architecture/` with a local README. Leave short-lived fixes and recovery notes in `documents/plans/`.
40. **Use plain domain terms.** Prefer "text", "narrative", "market activity", and "market overview". Avoid legacy market-media jargon in product/domain code and docs; technical dataframe duplication APIs are still fine.
41. **Knowledge graph is a prior, not evidence.** AQL can use the reviewed graph to find entities, paths, hypotheses, and graph change candidates, but final causal narrative still needs current evidence and claim support. Keep graph persistence owned by `services.knowledge_graph`; let AQL write through typed graph-service commit APIs with audit/rollback, using review escalation for risky changes, not ad hoc SQL or silent narrative-time mutation.
42. **Resolve graph subjects before graph search.** Do not pass full AQL narratives directly into KG node search. Extract symbols, aliases, and domain terms first; otherwise generic words like "company", "demand", "and", or "on" can create high-confidence false graph matches.
43. **Entity extraction must be independent and non-blocking by default.** Broad taxonomy and universe lookups can touch materialized storage. Keep shared entity extraction on feed metadata, KG aliases, claim entities, and optional LLM output unless a caller explicitly opts into heavier lookup. Do not make entity extraction an AQL-owned subsystem.
44. **Knowledge-graph exploration should be entity-first.** UI graph builders should extract and link entities before running graph search or expansion. Raw text search is useful fallback for short manual seeds, but linked entities make add/remove review safer and easier to audit.
45. **Large graphs need an overview before search.** Exploration pages should show a capped, ranked subgraph on first load. Empty screens make users guess what the graph contains; full graphs become unreadable.
46. **Disconnected graph components need their own layout space.** A single force-directed simulation can overlap independent subgraphs because no edges separate them. Lay out components independently, then pack them with padding before rendering.
47. **Graph visuals must show graph semantics.** If the stored model has directed edges, confidence, and severity, the visualization must encode those fields directly. Otherwise users are judging a simplified drawing, not the graph they are being asked to validate.
48. **Attention jobs should propose KG changes, not apply them.** Scheduled runs can extract entities and causal edges from fresh evidence, but core graph writes need review until proposal precision is measured. Materialize proposal rows first, then let the graph review UI commit approved deltas.
49. **Page summaries need one shared contract.** Market, stock, macro, and trading surfaces should pass structured page facts into one LLM-backed summary helper, then render the returned headline, watch items, gaps, and confidence. This keeps summaries consistent and lets downstream agents consume them without scraping UI text.
50. **Shared contracts still need shared evidence.** A common page-summary schema is not enough; agentic summary surfaces should reuse AQL / Zopedia for retained evidence, live evidence, ticker tools, and verification, then adapt that grounded output into the schema.
51. **Render paths stay cheap.** Main research features should render existing state first and make expensive AQL/LLM work explicit through a button or a scheduled job. Caching reduces repeated cost, but it does not make first-load agent runs acceptable.
52. **Batch labels from materialized snapshots.** Company names and display metadata should come from universe snapshots where possible. Per-symbol fallback is acceptable for a small selection, not for a full market table.
53. **Fixed market feeds materialize beside their summaries.** The Market Opportunity feed is derived from scheduled mover and momentum snapshots, so the attention job should persist the ranked feed and the UI should only select the requested focus/horizon from that materialized table.
54. **Materialized summary contexts must match UI contexts.** If a page summary is resolved by context signature, the job and UI must build the same compact context. Do not include job-only source row counts that the page no longer loads.
55. **Use compact guardrail references for repeated failure zones.** When mistakes/learnings get large, create a short reference file under `documents/reference/` that names the relevant IDs and the required architecture. Read that file before touching the same feature family again.
56. **Job-owned agentic work still needs bounded steps.** Scheduled materialization keeps page load fast, but it also needs per-step timeouts around external AQL/search/LLM paths, including downstream bundle writing and verification. Otherwise the job can hang before writing the cached outputs the UI depends on.
57. **Persisted job frames need explicit dtypes.** Review/proposal frames that mix optional text defaults with numeric values can fail only at parquet upload time. Coerce numeric review fields before handing frames to the pipeline store.
58. **Shared AQL in jobs is also a packaging contract.** If a scheduled job reuses AQL/Zopedia modules, the job image must copy the same dependency folders the UI/API image has, not only `services` and `pipeline`.
59. **Fallback contracts need end-to-end tests at the outer timeout layer.** It is not enough to test that the summary helper falls back when AQL raises. Also test that the scheduled job timeout wrapper writes the same `fallback` schema, because that is the row the UI actually reads.
60. **Ticker identity is not a metric.** In dense trading or research cards, render ticker plus company name as the row identity and use metrics only for numeric values. Narrow metric widgets clip symbols and hide the context needed to judge a setup.
61. **Trading signals need a visual audit trail.** A composite score should show its visible components, selected horizon, trend quality, and missing data. Otherwise users cannot tell whether the setup is driven by a real trend, a one-day move, or an unexplained internal rank.
62. **News-count summaries are metadata, not context.** Sentences like "6 recent articles over 4 days; tone is mixed" can explain coverage volume, but they should not fill Background or What Happened slots. User-facing context sections need substantive company or catalyst text, or a clear unavailable state.
63. **Slow company context belongs in its own dataset.** Company background changes slowly and can be prefetched monthly from universe/taxonomy/Wikipedia. Daily attention jobs should update catalysts and headlines, then merge the slow baseline only when the narrative text is missing or generic.
64. **Public reference APIs need polite batch defaults.** Even low-volume scheduled jobs should identify themselves and include a configurable inter-request delay. This keeps small tests and future larger runs from accidentally behaving like a scraper.
65. **Company names need source-aware cleanup.** Exchange/universe names often include share-class and legal suffix text that does not map to reference pages. Try the official display name first, then a cleaned legal-suffix candidate before falling back to generic company text.
66. **Prebuilt audio is tied to generated text.** Homepage audio length is controlled by the materialized `audio_text` from `attention-home-build`, not only the render-time display limit. Regenerate the job output after prompt changes, and store a text hash beside embedded TTS bytes so stale audio can be detected.
67. **Research agents should avoid execution-like market wording.** Prompts that say "trade candidates", "short/avoid", or "execution" can be rejected before the model sees the safety qualifiers. Use neutral watchlist and downside-risk language in LLM prompts, then map back to UI labels after generation.
68. **AQL sidecar calls need transient retries.** Interactive surfaces that call AQL tools inherit flaky web/search/source connections. Retry dropped connections once at the feature boundary and translate repeated transport failures into a human-readable data gap.
69. **Transport sanitization belongs at shared agent boundaries.** Fixing one feature wrapper is not enough when the same Zopedia agent powers multiple surfaces. The shared agent and UI shell should both translate dropped HTTP/model connections before raw provider exceptions reach the page.
70. **Reasoning-provider swaps need adapter seams.** Providers that expose reasoning traces may not share OpenAI/Azure strict JSON schema semantics. Add a provider adapter, capture the provider's reasoning field as trace metadata, and route it per agent before changing the app-wide LLM runtime.
71. **Runtime refresh triggers should use runtime credentials, not deployment tools.** Streamlit containers should not need Azure CLI to start a precompute job. Use managed identity plus Azure Resource Manager for in-app job triggers, with CLI only as a local developer fallback.
72. **Routers enrich chat requests; they do not decide whether the agent runs.** In chat-style research UI, deterministic routing should add direct matches and context metadata, then hand the request to the agent. Bare replies like "yes" also need to resolve against the prior assistant turn before enrichment so the agent receives an actionable continuation.
73. **Every model step in an interactive agent needs its own timeout.** Tool timeouts are not enough. A planner or final synthesis call can hang after useful evidence has already been collected, so bound each LLM step and degrade to synthesis or evidence-state fallback.
73. **Social state needs stable content anchors.** Reactions, comments, and share artifacts should attach to materialized run IDs, context signatures, tickers, bundle IDs, or content digests. Do not anchor durable interaction state to rendered markdown, card order, or `st.session_state`.
74. **Operational job controls belong in admin.** Feature pages should read materialized datasets and expose product actions only. Job starts, retries, and refresh controls live in Admin > Pipeline Jobs.
75. **Log-only trade actions should keep execution fields.** Even before Alpaca order placement is enabled, persist execution mode, broker, broker order id, and intended order payload so the future broker transition is an extension of the audit record.
76. **Required agentic horizons need fallback candidates, not only fallback status.** If AQL times out in a scheduled Trading Agent build, use the materialized opportunity feed to persist conservative low-confidence candidates and record the AQL gap. The UI should have something reviewable for every required horizon while still showing the evidence limitation.
77. **Interactive agents need deterministic evidence seeding.** For common query shapes, collect the obvious first evidence before asking an LLM planner: ticker context for ticker questions, all ticker contexts before comparisons, live event evidence for current catalyst questions, and the materialized homepage summary for broad "what matters" prompts. The planner should refine evidence, not spend latency discovering the first step.
78. **Generic tool summaries can hide the real answer.** Rich dataset payloads like `attention_home_1d` need a purpose-built LLM context extractor. Passing only object keys and run IDs makes the synthesizer claim missing current data even when the materialized narrative is present.
79. **Planning and synthesis can use different model latency profiles.** A reasoning model can be useful for tool choice and trace capture, but final synthesis after deterministic evidence seeding is mostly compression. Keep a scoped synthesis-model override so Zopedia can reduce latency without changing the app-wide LLM runtime.
80. **Interactive agent tools and hidden preparation steps need heartbeats and timeouts.** A visible planner heartbeat is not enough if the current step is inside a slow live-search tool or a prefetch keyword extractor. Bound each nontrivial external/LLM step, emit elapsed-time progress, and synthesize from collected evidence when a step times out.
81. **Auth-action URLs are separate from app routing.** Reset and invite tokens should force a logged-out auth screen, skip public-home shortcuts, and never restore cookies before the form is shown. Completing a reset should not create a session; users must authenticate with the new password.
82. **Session validity is dynamic.** Restoring a browser/API session must re-check `users.status`, active portfolio status, and active membership. Authenticated context is not just a non-expired session row.
83. **Zopedia parity starts headless.** Before renaming or polishing UI, prove the memory loop as source text -> SAA retained document -> chunks -> wiki pages -> graph links -> automatic guarded mutation. Transcript text already fits the SAA retention/search layer, but native ingest, durable wiki pages, source tracing, audit, rollback, and review escalation are the real integration gates.
84. **AQL must be the research-grade LLM boundary before Zopedia.** Adding wiki memory only improves every surface if attention summaries, page summaries, Trading Agent, stock pages, and chat all consume the same AQL evidence pack. Direct LLM calls can stay for metadata/routing/formatting, but not for independent market narratives.
85. **Fail closed instead of inventing fallback narrative.** If AQL or the formatter LLM cannot produce a grounded page summary, return an unavailable state from the scheduled summary artifact. Do not turn structured rows into hardcoded summary prose or ask the user to repair the missing artifact from the feature page.
86. **Feature pages consume generated research; Admin operates jobs.** Product screens should show current answers, evidence, progress, and quiet unavailable states. Manual analysis buttons, FRED load controls, materialized/scheduled/precomputed language, and run-job controls belong in Admin/docs/logs, not in Broad Economy, Market Explorer, or Stock Investigator.
87. **Zopedia memory is SAA-owned wiki state.** Native Zopedia should persist source-backed pages, links, source URLs, mutation logs, and escalated proposals in SAA tables, then expose them as agent tools. AQL can read and cite those pages, and safe writes should go through explicit typed commit APIs with audit/rollback.
88. **YouTube transcript support needs provider diagnostics.** Even with a transcript library and timedtext fallback, YouTube can IP-block server environments. Return a clear unavailable status and allow pasted transcripts/source text so Zopedia ingestion still works.
89. **Macro graph thresholds must preserve obvious shared-role clusters.** Rates ETFs sharing sector, rates role, and macro tags should clear the graph edge threshold. If graph policy changes, test obvious rates/oil/defensive clusters end to end, not only individual candidate scoring.
90. **Auth-action cleanup has two phases.** Opening a reset/invite link must clear existing sessions before rendering the form; any later successful login must also remove the auth-action query params so refreshes and new tabs restore the new session normally.
91. **Browser persistence needs a completed render.** A cookie-setting component is not durable until the frontend mounts it. After login, update session state, render the cookie sync, and continue into the authenticated app instead of forcing an immediate rerun.
91. **Model access needs one named product boundary.** Feature code and jobs should not call the raw LLM loader directly. Route model access through a shared Zopedia/AQL boundary that requires a named surface, then scan for violations in tests so new orphan model calls fail fast.
92. **Zopedia quality needs answer-level evals, not only tool checks.** A tool trace can show `zopedia.search_pages` while the answer still says no memory was found. Product evals must inspect the final answer for memory use, page reads, citations, limitations, and contradiction with the tool state.
93. **Long natural-language memory search needs a tolerant fallback.** SQL full-text filters can miss useful pages before the app-level scorer gets a chance to rank them. For Zopedia wiki search, use strict full-text first, then fall back to a bounded candidate set and lexical scoring when the strict query returns nothing.
94. **Memory search should usually be followed by page read.** A Zopedia search result gives a map; the answer should read the page before treating memory as evidence. The planner contract and evals should check that memory-backed answers actually read and cite pages.
95. **Evidence contracts are not query keyword routers.** Zopedia can require grounded behavior — company questions need fundamentals/news/history, macro questions need local data first, stale memory needs guarded mutation, false premises need verification — without hardcoded query word lists. Put the standard in the planner contract and eval gates, not in code branches that pretend to classify the user's intent.
96. **Hard questions need evidence coverage, not only tool traces.** A trace that shows one plausible tool can still produce an overconfident answer for a multi-part question. Track required evidence slots, filled slots, missing slots, and answer confidence before final synthesis.
97. **Zopedia parity is a runtime and maintenance contract, not just wiki storage.** Source immutability, page schemas, backlinks, godnodes, compaction, merge, tool budgets, two-phase tool resolution, source tracing, automatic guarded mutations, and answer-level evals all have to exist before calling the feature complete.
98. **Zopedia UI should lead with reasoning trace and source ingestion, not graph decoration.** Streaming tool/reasoning progress, custom uploads, source tracing, page inspection, mutation audit, rollback, and review escalation are core. Full graph exploration should wait until provenance, backlinks, and godnodes make the graph semantically meaningful.
99. **Zopedia should auto-improve memory when evidence is strong enough.** Review queues are still needed for risky, ambiguous, destructive, or low-confidence changes, but the target product is an autonomous memory loop. Safe source-backed page creation, source attachment, link addition, aliasing, contradiction annotation, and timestamped fact updates should commit through typed APIs with audit and rollback metadata.
100. **Zopedia maintenance is core product behavior.** A durable wiki memory system degrades without compaction, duplicate detection, link repair, staleness checks, contradiction handling, source-coverage checks, and maintenance reports. Treat maintenance as part of the engine, not an advanced UI follow-up.
101. **Provider reasoning belongs in the shared LLM adapter.** DeepSeek `reasoning_content` should be captured once in `services.llm.DeepSeekChatJSONClient` and carried through the shared response contract. Do not create Zopedia-only provider overrides when the intended change is the global LLM layer.
102. **Wiki source refs need a read-through tool.** A page-level source list is not enough for grounded answers. Agents need a stable `read_source` operation that can open Zopedia source pages, retained SAA chunks, retained source documents, and URL refs from the same source-ref contract.
103. **Deploy scripts must preserve explicit runtime overrides after sourcing generated env files.** `VAR=value deploy_script.sh` is not reliable if the script sources `infra/.generated/deployment.local.env` afterward and treats sourced values as overrides. Capture requested env first, restore after source, and clean provider-specific stale env during deployment.
104. **Scheduled job env needs last-wins normalization.** Common runtime env belongs on every job, but per-job overrides must replace common entries before calling Azure. De-duplicating by env name keeps one deploy path while still allowing special timeouts or job-specific knobs.
105. **Upload ingestion belongs behind the memory service contract.** The UI should only collect the file. Decoding text/PDF bytes, rejecting unreadable binary, preserving filename/content metadata, and passing provenance into generated pages belong in Zopedia/SAA services so API and agent paths can reuse the same behavior.
106. **Answer critique belongs at the shared agent boundary.** A judge pass should review the draft against the exact tool evidence before the answer leaves Zopedia, then revise or lower confidence through the same result contract. Putting this in page-specific UI code would miss API, chat, and future agent surfaces.
107. **Automatic memory writes need a ledger at the write boundary.** Source-backed Zopedia ingest should commit page rows and mutation audit rows in the same service transaction, then expose the audit through agent tools. A separate review/proposal table is not enough for autonomous memory improvement.
108. **Rollback should execute from stored snapshots, not fresh inference.** If an audited Zopedia mutation has before/after page snapshots, undo should restore those rows and archive newly created rows directly. Do not ask an LLM to reconstruct prior state.
109. **Zopedia maintenance belongs in jobs, not chat.** Chat should read maintenance reports and mutations. Backlink rebuilds, community/godnode indexing, stale/orphan/source checks, and memory-health reports should run as scheduled jobs and write durable SAA rows.
110. **Typed memory mutation is the source of truth.** Safe automatic Zopedia writes should enter through one service function that creates before/after state, evidence refs, audit rows, and rollback handles. Agents and UI should not patch page rows directly.
111. **Risky memory edits should still use the same contract.** Delete, merge, rewrite, source removal, and low-evidence changes should become proposals through the typed mutation API until the executor has measured precision and judge coverage.
112. **Feature pages read memory health; admin owns operations.** Showing latest Zopedia health, communities, issues, and rollback actions is product behavior. Triggering or retrying scheduled maintenance remains an admin/pipeline concern.
113. **Dev job deploys need a runnable proof.** Creating a scheduled Container Apps job is not enough for engine work. Start one dev execution, verify completion, and record the counts before calling the job wired.
114. **Zopedia UI should hide engine plumbing by default.** Proposals, mutations, and health are still core engine state, but they should be automatic and agent-readable. The main product surface should be chat history, upload, trace, citations, and a compact health signal.
115. **Streamlit mobile checks need Streamlit-specific state assertions.** Selectbox selected values can live in the combobox `aria-label`, not text content, and Streamlit may scroll `stAppScrollToBottomContainer` instead of the document. Browser checks should assert the selected value and reset Streamlit scroll containers before screenshots.
116. **Agent-run analysis needs a sandbox, not shell access.** For EDA and scikit-learn, let the agent choose datasets and generate code, but execute only in a bounded runner with approved dataframe inputs, no network/secrets/shell, stored artifacts, and source refs.
117. **Agent analysis inputs should enter through QueryService.** Letting generated code fetch data recreates orphan data paths and secret/network risk. The agent should name approved datasets and params, then the runner receives already-materialized dataframes plus provenance.
118. **Shared data dependencies need major-version caps across containers.** The UI/API Python 3.10 images and pipeline Python 3.11 images can resolve different latest wheels. Pin pandas below the next major release until the whole stack is tested against that major version.
119. **Chat history is product state, not an agent run log.** The run log is for audit/debug. A conversational product needs thread and message tables that can replay assistant payloads, traces, citations, memory updates, and confidence.
120. **Automatic memory needs a post-answer maintainer.** Planner-time tools can update memory when the user asks directly, but normal answers need a bounded post-answer pass that reviews final evidence and routes safe writes through typed mutations or risky writes through proposals.
121. **Synthetic sources are not citations.** Eval/debug pages can live in the same wiki tables, but normal search and answer citation strips should filter them through source metadata and URL validity. A fake URL like `eval.local` is useful for test provenance, not for user-facing evidence cards.
122. **Zopedia controls need product tabs, not stacked expanders.** History, source attach, and admin/debug are different jobs. Separate tabs make the chat surface cleaner and keep engine state inspectable without making it look like the main workflow.
123. **Answer text is an interaction surface.** Zopedia answers should be sectioned Markdown, then rendered as selectable passages. A selected passage can become the next scoped query, which is cleaner than adding more global buttons around a dense answer blob.
124. **Browser-path validation beats implementation inspection for agent UX.** A Zopedia change can pass unit tests while the live page still exposes tool names, unrelated cards, or unreadable answer controls. Run the rendered chat path before calling the experience acceptable.
125. **Confidence is a coverage contract.** The judge can sound confident, but the shared agent boundary should still cap displayed confidence when evidence coverage is thin.
126. **Responsive helpers should be the only column boundary.** In Streamlit, broad mobile CSS can rescue many layouts, but routing every column through one responsive helper makes mobile stacking, desktop parity, and future page audits much simpler.
127. **Mobile first viewport should answer before it visualizes.** Dense graph or chart surfaces can be useful, but on phone screens the narrative or primary action should come first and the visualization should be optional or below the summary.
128. **Feature flags are deployment state.** A mobile implementation is not actually live until the Container App env carries the mobile flag and layout default. Deployment scripts should preserve those env vars the same way they preserve LLM/runtime config.
129. **Trace expansion is part of the trace contract.** If Zopedia advertises live reasoning/tool progress, the UI must keep that panel open during live updates and carry the same open state into the saved chat message. Treat open/closed state as product state, not widget decoration.
130. **Zopedia should feel like a research conversation, not a control panel.** History, source attach, admin, memory health, citations, and trace are supporting structures. The default visual hierarchy should be active thread, answer, evidence, composer; everything else belongs in rails, drawers, chips, or contextual actions.
131. **A high-bar plan needs a single execution spine.** Keep current status, blocker, roadmap, gates, and immediate next step aligned. If a plan says a feature is both "chat-first" and "not shippable," fix the plan before implementing.
132. **Separate implemented capability from proven product quality.** For Zopedia, judge/memory/mutation/maintenance code exists, but the remaining bar is measured behavior: hard-question evals, false-premise resistance, source coverage, safe automatic updates, rollback proof, and dev browser-path validation.
133. **Anti-fragility starts with guided-correction capture.** When a user shows the agent that a tool path exists, the system should mine the thread, identify the failed assumption, create a regression eval, update tool-affordance memory or planner contracts, and verify the next run reaches the answer without the same rescue.
134. **Good agent answers need evidence-slot planning, not just more tools.** The bond-yield dry run worked because it filled macro move, representative instruments, observed returns, statistical context, and causality caveats. The system should teach agents to plan/fill evidence slots and fall back across tool levels before saying data is unavailable.
135. **Self-improvement needs a ledger and promotion gates.** For Zopedia, "learn from mistakes" means persisted learning events, structured critic output, regression evals, safe tool-affordance or planner updates, replay verification, and regression monitoring. Without those gates, self-improvement becomes prompt drift.
136. **Empty rows need cause labels.** In the bond-yield thread, ETF `daily_movers` was empty because materialized movers excluded ETFs, event significance was empty because the post-event window had too few observations, and analysis was rejected because code/input contracts failed. Agents should surface the precise empty-result cause and try primitive fallback data before saying data is unavailable.
137. **Agent learning plans must include source-level tool fixes.** If a failure comes from ambiguous tool contracts, fixing only prompts or planner behavior is too shallow. The plan should require structured empty-result metadata, fallbacks in the tool layer, and evals that prove the agent no longer treats tool gaps as data gaps.
138. **High-bar plans need product proof and promotion rules.** Backend phases are not enough for Zopedia quality. The plan needs rendered UX gates, named golden scenarios, learning-update promotion rules, rollback requirements, and dev runtime proof before a feature can be considered excellent.
139. **Small tool previews can erase the evidence the model needs.** A daily-movers basket with five instruments is not useful if the LLM context samples only three rows and hides the missing proxy. Keep small evidence baskets visible in full.
140. **Partial materialized matches still need fallback.** If a materialized snapshot returns some requested symbols but drops the important ones, retry the primitive/on-demand path before letting the agent infer that the missing symbols have no data.
141. **Self-improvement needs an executable service, not only a plan.** A rescued chat should flow through one learning service that detects the failure, persists a ledger row, generates an eval, applies safe reversible memory updates, and exposes a job summary.
142. **Generated evals need literal failure strings.** High-level rules like "do not claim data is unavailable" are useful for humans, but regression tests need concrete forbidden answer patterns such as `stock data is unavailable`, `tool_call_id`, or `run_id`.
143. **Learning jobs need runtime proof, not only local proof.** After wiring an anti-fragile service, verify the deployed job image, provider env, one manual execution, and job counts. A local DB dry run is useful but does not prove the scheduled engine is live.
144. **Learning events need promotion states.** Detecting a failure, generating an eval, and applying a safe update are not the same as proving improvement. Replay the eval and mark events `verified` or `regressed` so the system can distinguish durable learning from hopeful mutation.
145. **AQL/Zopedia needs one orchestration spine.** Chat, live research, homepage summary, page summary, evidence-pack generation, critique, and maintenance should be modes of one engine contract, not separate endpoints with shared helper imports. Surface wrappers can differ, but planning, tool access, evidence capture, memory reads, and write policy must be centralized.
146. **Analysis repair needs input profiles and proof.** The latest Zopedia bond-yield thread showed the repair pass firing but returning code that still failed on indentation and dtype assumptions. Repair prompts should include actual frame columns/dtypes/samples, and the sandbox should normalize generic formatting defects and surface stdout/tables so a repaired run is useful to the final answer.
147. **Live news tools need internal budgets, not only outer tool timeouts.** The oil/geopolitics thread showed `research.live_event_evidence` timing out because it chained helper LLMs, SerpApi, Tavily, and symbol news under one 25s wrapper. Interactive news tools should use direct-query fallbacks, bounded helper calls, short provider timeouts, partial results, and contextual follow-up resolution so the agent can answer with whatever evidence arrived.
148. **Tool serialization and previews are part of the data contract.** The long-term trend thread showed `momentum_profiles` failing because an array-valued sparkline crashed JSON conversion, then `price_history` worked but the model treated a tiny sample as the full window. Data tools should serialize array-like cells safely and provide LLM-facing first/latest/return summaries for time series, not only row samples.
149. **Tool context should be summary-first.** Raw stdout, stderr, traceback, and logs are useful for debugging but expensive and noisy inside planner/final prompts. Normal tool results should expose counts, hashes, shapes, metrics, and artifact summaries; exact logs should require an explicit raw-output tool call.
150. **Visible planner/status prose is product content.** Zopedia's reasoning/status trace should remain visible when useful, but it must be rendered as a polished research narrative: readable step titles, compact arguments, paragraphs, preserved tables, and stable expansion. Do not treat visibility itself as the bug.
151. **Old endpoint names should be removed, not tolerated.** If AQL/Zopedia is the product spine, jobs, scripts, evals, and UI should call `run_aql_zopedia_agent`; the old Omnibar agent loop can remain only as a private implementation detail behind the engine boundary.
152. **Mobile auto-detection needs a normal-URL proof.** Streamlit server-side request headers may not expose the browser user-agent reliably enough for layout routing. For mobile web rollouts, verify the plain deployed URL on an iPhone-sized browser, then verify explicit desktop override separately.
153. **Mobile rollout defaults must preserve desktop.** Dev is the validation target for mobile web, but `STREAMLIT_LAYOUT_MODE_DEFAULT=mobile` forces desktop browsers into the phone shell. Use `STREAMLIT_LAYOUT_MODE_DEFAULT=auto` with a client-side phone redirect, then verify both a desktop viewport and an iPhone viewport against the plain deployed URL.
154. **Broad Economy summaries belong to the macro job.** The Broad Economy Zopedia Summary should be generated when FRED macro data refreshes, not as a side effect of homepage attention shortlist generation. Exact context matches are useful, but the page should fall back to the latest valid Broad Economy summary instead of showing a manual analysis button when formatting or lookback context drifts.
155. **Partial dataset writers need surface-aware reads.** If multiple jobs write different rows to the same materialized dataset, the reader must find the latest valid row for the requested surface instead of assuming the newest dataset version is complete.
156. **New page versions must carry forward every rendering concern.** When building v3 of a page (homepage, dashboard, etc.), audit the v2 renderer for every feature it renders — audio players, share buttons, debug traces, replay controls — and explicitly include or consciously drop each one. A feature matrix checklist before shipping prevents "where did X go?" moments.
157. **Token-to-information ratio is a first-class UX metric.** Every rendered word must help the user make a decision. Critique summaries, raw source/tool names, verbose "no data" explanations, and low-confidence labels are internal plumbing — they belong behind an admin debug toggle, not in the user view. The test: "If I removed this element, would the user lose decision-making ability?"
158. **LLM prompt tightness drives output quality more than post-processing.** Fixing verbose summaries at the prompt level (word caps, skip-empty-section instructions, structured section templates) is more effective and durable than trying to trim output in the UI. Post-processing is a bandaid; the prompt is the fix.
159. **Degraded states still need product hierarchy.** If cached or materialized product content is available, show it before setup/debug instructions. Runtime setup details such as Key Vault env vars, secret names, and shell commands belong in Workspace Status, Admin, logs, or docs — not above the user's market narrative.
160. **Completed agent traces should be answer-first.** Live Zopedia progress can stay expanded while work is running, but completed answers should land on the answer, citations, and compact trace summary. Raw model reasoning and memory-action deliberation should be available on demand, not the default viewport.
161. **A rendered summary and its narration must share one payload.** If Home renders a Zopedia market summary, its audio should be generated from that same Zopedia answer row. Keeping the older homepage summary audio beside a newer displayed answer creates a product-level mismatch even when both systems are individually working.
162. **Custom-domain health needs DNS-path checks.** Azure Container Apps can show a healthy revision and a valid custom-domain binding while the apex domain still resolves somewhere else. Verify apex and `www` DNS, `/_stcore/health`, and a real browser WebSocket session before calling the public site healthy.
