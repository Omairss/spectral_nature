# v0.5 Roadmap

Date: 2026-06-22

## Purpose

This document consolidates the current open plans into a v0.5 execution order.
It answers four questions before implementation:

1. Are the plans still fresh, or are they stale?
2. Do any plans conflict with each other?
3. Is there a better alternative ordering?
4. Which tasks can run in parallel?

The guiding rule is simple: v0.5 should strengthen the shared AQL/Zopedia and
pipeline spine before adding more product surfaces.

## Requested Priority Buckets

### P0

- Pipeline simplification.
- Zopedia retrieval / tool discovery.
- Ticker business model stack.
- Zopedia company / news business resolution.
- `HARDCODE_CLEANUP_MATRIX`.

### P1

- Attention anomaly detector.
- Clickable stock summary.
- Attention FRED integration.
- Module boundary audit.

### P2

- Everything else.

## Conflicts

1. **Clickable stock summary conflicts with pipeline simplification.**
   The clickable plan calls `run_omnibar_agent` and runs research on click. P0 wants one AQL/Zopedia entrypoint and no hidden heavy UI work. The clickable plan must be rewritten around materialized claim IDs and `run_aql_zopedia_agent`, or deferred.

2. **Attention anomaly detector and FRED integration both touch scoring.**
   The anomaly plan wants ranking based on standardized data abnormality. The FRED plan adds macro alignment/conflict scoring. These should not become two competing score systems. v0.5 should define one Attention Scoring v2 contract: anomaly is the base rank; macro/FRED adds context, shadow fields, and only later a gated adjustment.

3. **Hardcode matrix P0 labels conflict with its own progress snapshot.**
   The matrix says its P0 items are complete. Treating the old P0 labels as current P0 would reopen solved work and distract from current source-level failures. The matrix should be re-audited and only current blockers should enter v0.5.

4. **Pipeline simplification deletion work can break ticker business and company-resolution work.**
   The company stack currently still runs through modules with Omnibar-era names. Deleting or renaming the agent loop before locking behavior can break the business-memory path. Add behavior tests first, then move ownership.

5. **Business-memory long-running jobs conflict with hard required-output failure unless contracts are explicit.**
   A background business-research stage can have gaps for some symbols. v0.5 should define which outputs are mandatory for the job and which rows may be `insufficient_evidence` or `unavailable`. Required job failure and honest per-row gaps are compatible only if this contract is clear.

6. **Module boundary audit overlaps with pipeline simplification.**
   Running them separately can create duplicated renames and import churn. Use module-boundary rules as acceptance gates for pipeline simplification.

## Better Alternative

Keep the requested P0/P1/P2 buckets, but execute them through three integrated workstreams.

### Workstream A: Spine And Contracts

This is the first v0.5 track.

- Build or refresh the pipeline simplification inventory.
- Add golden behavior tests before deletion.
- Move AQL/Zopedia ownership away from Omnibar names.
- Delete fallback prose only after typed failure contracts are tested.
- Fold module-boundary checks into the acceptance gates.

Why this is first: every other track depends on a reliable engine boundary and clear artifact ownership.

### Workstream B: Company Memory And Retrieval

This is the second v0.5 track and can begin in parallel with inventory work.

- Implement Zopedia retrieval/tool discovery as shared search and tool contracts.
- Add BM25, pagination, missing-slot planner behavior, and evals.
- Prove ticker business stacks and Zopedia company/news resolution in scheduled dev runtime.
- Promote only source-backed company memory through proposals or safe writes.
- Ensure Attention/Home/Trading consume the same company-memory artifact instead of re-researching.

Why this is second: it makes current market/company answers better without adding another UI surface.

### Workstream C: Attention Scoring v2

This is the P1 track after P0 contracts are stable enough.

- Merge the anomaly detector and FRED integration into one scoring contract.
- Start with replay and shadow scoring.
- Use anomaly score as the base attention rank.
- Use macro/FRED relationship checks as context and gated adjustment, not a competing ranker.
- Do not promote live ranking until replay windows prove better ordering.

Why this waits: attention scoring touches the main product feed and should not move while fallback/ownership cleanup is unstable.

### Rewrite Or Defer Clickable Stock Summary

Do not implement the current plan as written.

Better version:

- During materialization, split Zopedia ticker summaries into claim IDs with source refs and context.
- Render claims as selectable passages.
- On click, either show precomputed context or start an explicit Zopedia follow-up action through the shared engine.
- Never call Omnibar, never run silent UI research, and never parse arbitrary sentences with brittle length thresholds.

This is P2 unless the interaction is needed to validate the company-memory layer.

## v0.5 Execution Order

### P0.0: Current-State Inventory

Deliverables:

- Refresh the simplification inventory against the current worktree.
- Re-audit `HARDCODE_CLEANUP_MATRIX` and mark only current blockers.
- Confirm current owners for Zopedia agent loop, retrieval tools, company-memory datasets, Home summary/audio, and Attention scoring.

Exit criteria:

- One current deletion/ownership list exists.
- No implementation begins from stale line counts or old Omnibar assumptions.

### P0.1: Behavior Locks

Deliverables:

- Golden tests/probes for Home summary/audio, Zopedia chat, ticker business stack, news business resolution, Attention build, and one dev job run path.
- Failure-contract tests for `failed`, `unavailable`, and `insufficient_evidence`.

Exit criteria:

- The tests protect user-visible behavior and materialized dataset contracts, not old module names.

### P0.2: AQL/Zopedia Retrieval And Tool Discovery

Deliverables:

- BM25 as a shared lexical signal for Zopedia pages, retained chunks, and tool metadata.
- Cursor pagination for search-style tools.
- Agent-facing tool search over the shared catalog.
- Planner rule: only search tools or paginate when an evidence slot is still unfilled.
- Evals for exact terms, long wiki queries, tool lookup, and after-first-page evidence.

Exit criteria:

- The agent can find evidence/tool capabilities without a giant prompt or hardcoded classifier.

### P0.3: Company Memory Runtime Proof

Deliverables:

- Scheduled dev proof for `zopedia_ticker_business_model_stacks`, `zopedia_news_business_resolutions`, and `zopedia_company_business_memory_pages`.
- Qualitative review over several tickers.
- Proposal/safe-write policy proof.
- Attention/Home/Trading read the company-memory artifacts instead of rebuilding the same story.

Exit criteria:

- A new news item resolves against source-backed company memory with readable gaps and no broad-theme leakage.

### P0.4: Simplify And Delete

Deliverables:

- Move Zopedia agent ownership out of Omnibar-named modules.
- Remove fallback prose from core paths.
- Collapse Home summary/audio into one typed artifact.
- Make required job outputs required.
- Split job dispatcher only after contracts are locked.

Exit criteria:

- Old names and fallback paths are gone from production code except explicit migration aliases at the boundary.

### P1.0: Attention Scoring v2 Replay

Deliverables:

- Prototype anomaly scoring over recent historical frames.
- Calibrate FRED/macro relationship checks against replay windows.
- Compare current score, anomaly score, macro-shadow score, and final proposed score.

Exit criteria:

- Shadow scoring improves ordering without graph/news gating or unstable prediction claims.

### P1.1: Attention Scoring v2 Integration

Deliverables:

- Replace bucketed candidate selection with anomaly ranking behind a config flag.
- Keep macro/FRED as shadow or gated adjustment.
- Preserve `home_payload` shape while improving candidate ordering.
- Add config override loading to pipeline jobs if admin knobs are kept.

Exit criteria:

- Default mode has no ranking regression.
- Live mode is gated and has replay evidence.

### P1.2: Boundary Cleanup

Deliverables:

- Import-boundary tests match the new ownership.
- Remaining compatibility shims are deleted or moved to explicit migration boundaries.
- Data access does not import AQL internals.

Exit criteria:

- Import direction matches the pipeline simplification contract.

### P2: Everything Else

Examples:

- Clickable stock summary after rewrite.
- Full graph explorer and advanced graph modes.
- Wiki behavior/admin config panels.
- Inbound mail.
- iPhone app endpoints.
- Security history rewrite and clone cleanup.
- UI/UX polish not required for P0/P1 proof.

## Parallel Work

### Can Run In Parallel Now

1. **Inventory and behavior locks.**
   One person can build the simplification inventory and golden tests while others avoid touching deletion targets.

2. **Zopedia retrieval design and eval fixtures.**
   BM25/pagination/tool-search interfaces and eval cases can be designed while inventory work runs. Implementation should avoid renaming the agent loop until P0.1 is stable.

3. **Company-memory qualitative proof.**
   Scheduled dev proof, probe review, and dataset-quality review can run while the inventory is built, as long as it does not rename shared agent modules.

4. **Hardcode matrix re-audit.**
   This is independent documentation/static inspection work. It should produce current blockers, not code changes yet.

5. **Attention Scoring v2 replay prototype.**
   Offline/replay-only anomaly and macro scoring can run in parallel. Do not wire live ranking until P0 contracts stabilize.

### Can Run In Parallel After P0.1

1. **Retrieval implementation and company-memory runtime proof.**
   They touch related agent/tool paths, so keep one shared contract owner and coordinate merges.

2. **Home summary/audio contract and renderer extraction.**
   These can run together only after the typed artifact is defined. Presentation extraction should not invent data logic.

3. **Module-boundary tests and shim deletion.**
   Boundary tests can be added while deletion work progresses, but each deleted shim needs a single owner.

### Should Not Run In Parallel

1. **Deleting Omnibar modules while changing retrieval tools.**
   Both touch the agent/tool boundary and can easily break Zopedia behavior.

2. **Attention anomaly live integration while FRED macro scoring changes live ranking.**
   Combine them into one scoring contract and run replay first.

3. **Hardcode cleanup in `attention_home_1d.py` while anomaly detector rewrites scoring.**
   That is the same surface. Do the anomaly contract and config cleanup together.

4. **Renderer extraction while changing Home payload shape.**
   Stabilize the payload, then move rendering.

5. **Clickable stock summary while pipeline simplification deletes Omnibar paths.**
   The current clickable plan depends on stale agent naming and UI-triggered research.

## Recommended Decision

Proceed with v0.5, but do not treat the requested P0 list as five separate projects.

The recommended v0.5 shape is:

1. P0 starts with current-state inventory and behavior locks.
2. P0 then splits into two coordinated tracks: spine simplification and company-memory/retrieval proof.
3. P1 combines Attention anomaly and FRED into one replay-first Attention Scoring v2 track.
4. Clickable stock summary is rewritten before implementation and likely moves to P2.
5. `HARDCODE_CLEANUP_MATRIX` becomes a current re-audit feeding P0/P1, not an old-priority checklist copied forward.

This ordering preserves the user's priority intent while reducing conflict and avoiding more feature-local patches.
