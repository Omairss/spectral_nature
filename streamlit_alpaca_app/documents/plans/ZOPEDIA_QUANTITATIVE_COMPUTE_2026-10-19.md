## One research engine, isolated computation

The existing research engine continues to own the investigation: question interpretation, acquisition, model formulation, execution decisions, review and final writing. A compute executor owns only running submitted numerical programs against declared inputs and retaining their results.

1. Extend the shared analysis tool contract to submit computation and return an execution ID promptly. Status, output inspection and cancellation refer to that ID.
2. Attach computation to the existing owner, environment, conversation and research run. Persist the submitted code revision, input manifest and resource allocation before dispatch.
3. Add a durable waiting-for-computation continuation. The research worker checkpoints and yields while computation runs; completion wakes the same investigation. Waiting must not consume model tokens through repeated status questions or occupy an HTTP request.
4. Reuse existing claim/lease/cancellation ownership. Submission and result adoption must tolerate duplicate delivery, prevent overlapping active attempts and publish one accepted result per logical execution. An interrupted attempt can be recorded and retried; do not claim exactly-once physical execution across crashes.
5. Distinguish admission/queue expiry, execution wall time and active research/model budgets. Waiting for an admitted computation must not exhaust the current five-minute research clock. Retain a separate total investigation expiry and spend ceiling.
6. Cancel through to the actual compute process. Preserve completed outputs and distinguish cancelled, failed, partial and successful execution. Arbitrary programs cannot resume at an arbitrary instruction; support explicit intermediate outputs and restart the unfinished step when necessary.

Local development and cloud execution should consume the same manifest and emit the same result contract. An executor is infrastructure, not a second planner or a provider-managed agent session.

## Modelling discipline inside the existing agent

Use the LLM to formulate and revise the model. Do not route financial intent through fixed ticker/phrase rules, force all problems into a DCF, or restrict discovery to canned formula templates. Persist the following as inspectable parts of the investigation, without requiring a separate model call for every item:

1. **Define the question.** Identify target quantity, horizon, as-of time, population/universe and whether the request asks for description, a conditional scenario, an empirical forecast or a causal claim. Let the agent resolve consequential ambiguity and ask the user only when it cannot reasonably infer the intended quantity.
2. **Acquire and reconcile inputs.** Inspect actual source values and coverage. Reconcile entity identifiers, reporting periods, currencies, scales, adjustments, sampling frequency and definitions. Carry missingness and disputed values through the analysis; do not silently fill unknowns with zero or manufacture historical observations.
3. **Make assumptions inspectable.** Separate sourced observations, user assumptions, estimated parameters and model choices. Link important assumptions to their effect on the result. The model should choose useful scenarios and sensitivity ranges from the problem and available evidence.
4. **Execute the numerical work.** Bind calculation-backed claims to outputs of the relevant successful execution and its actual input/code revision. A code block in an answer, a tool submission or a failed execution does not count as a completed calculation. Preserve independently supported research if computation fails.
5. **Inspect and challenge results.** The agent examines data coverage, executable code, actual tables, diagnostics and important source passages, then chooses further calculations or acquisition. Deterministic checks verify applicable arithmetic and structural contracts; LLM review assesses whether the model answers the question and whether its economics/statistics are defensible.
6. **Revise and communicate.** Retain the original and revised execution, explain consequential assumptions, show useful sensitivities and tie the final numbers to the computed outputs. Preserve useful findings when a reviewer is wrong or unavailable; avoid a confidence threshold that turns all criticism into an automatic veto.

Examples of problem-dependent investigation include rolling stability and common drivers in a correlation study; period alignment and debt/cash/dilution reconciliation in valuation; and training-only transformations, chronological validation and future-information leakage review in forecasting. These examples guide evaluation; they are not query-specific hardcoded policies.

A scenario distribution is not automatically an empirically calibrated forecast. Forecast evaluation needs declared targets/horizons, suitable simple baselines, time-separated evaluation and eventually resolved prospective predictions. Preserve what data was actually available at the forecast date; frozen retrieval alone does not remove an LLM's possible knowledge of later events.
